# EmoPlay 文档规范（docs/ 写作与维护标准）

> 本文件是 EmoPlay 仓库 `docs/` 的写作与维护标准，改编自 telegram-bot 项目的
> `DOC-STANDARD.md`（/home/emo/code/telegram-bot/docs/DOC-STANDARD.md），按桌面应用场景调整字段。
> 所有新写、改写的文档都要满足这里的硬性要求；规范本身随实践演进，改动需在提交信息里写明理由。

## 一、三条底线

1. **数字必须实测，写明来源。** 测试数来自 `flutter test` 输出、门禁结果来自工作流 gate 日志、
   CI 结论来自 `gh run list`。禁止写"大约""可能有几十个"——拿不到数就写"未测"，不要编。
2. **讲「为什么」，不只讲「是什么」。** 每一条结论都要能让读者回答：当时为什么这样做？
   不这样做会出什么事？纯清单式 changelog 不合格。
3. **坏消息必须写。** 未做项、已知限制、失败过的尝试、需要人工补的步骤，一律单列章节。
   只写好话的文档视为不完整。

## 二、放哪、叫什么

| 类型 | 目录 | 命名 | 例子 |
| --- | --- | --- | --- |
| 更新记录 | `releases/` | `RELEASE_YYYY-MM-DD.md`；同日多批加主题后缀 | `RELEASE_2026-11-10_QUALITY_ENGINE.md` |
| 工作报告 | `reports/` | `WORK_REPORT_YYYY-MM-DD.md`（一轮工作）/ `PROJECT_REPORT.md`（长期总报告） | — |
| 审计 | `audits/` | `AUDIT_主题_YYYY-MM-DD.md` | `AUDIT_PORT_PARITY_2026-11-10.md` |
| 手册 | `guides/` | 大写下划线 | `BUILD_GUIDE.md` |
| 交接/路线图 | `docs/` 根 | `HANDOVER.md` / `UPGRADE_ROADMAP_YYYY-MM-DD.md` | — |
| 迁移规格 | `docs/` 根 | `SPEC.md` / `PORT-MAP.md` / `STRIP-LIST.md` / `DOC-STANDARD.md` / `OVERNIGHT-LOOP.md` | — |

规则：日期一律 `YYYY-MM-DD`；文件名只允许字母、数字、`_`、`-`、`.`，不要中文文件名；
同一主题的系列文档保持同目录，用日期/主题后缀区分，不用 `_PART2`。

## 三、通用骨架

除索引外，每份文档**开头 10 行内**交代清楚：

```markdown
# 标题（一句话说清这是什么）

| 项       | 值                                            |
| -------- | --------------------------------------------- |
| 状态     | 生效中 / 已完成 / 已取代 / 提案（未实施）     |
| 日期     | 2026-11-10（最后实质性更新）                  |
| 适用版本 | git `<短哈希>`（可省略）                      |
| 相关     | 关联文档、issue、CI run                       |
```

- 只有**一个 H1**；章节用 `## 一、二、三`（中文数字）或英文短语，同一文档不混用。
- 每节先说结论，再说细节；表格只放可枚举事实，解释写进正文。
- 代码块标语言，命令可直接复制执行；不写密钥、Token、密码。

## 四、各类文档的必备内容

### 4.1 更新记录（`releases/`）——读者是用户

1. **引语**（blockquote，2–5 行）：这轮发布用户能感知到什么、修掉了什么隐患。
2. **元信息表**（字段固定）：`版本`（git 短哈希 + 时间 CST）、`平台`（Linux 容器验证/其他待验证）、
   `自动化测试`（`N 文件 / M 用例全绿`——与上轮对比）、`静态检查`（flutter analyze 结论）、
   `CI`（GitHub Actions run 结论）。
3. **分章正文**：新功能写**默认值的选择理由**；修复写**根因**，不只写现象。
4. **已知取舍**：做不到的、留待下轮的、有风险的。

不写内部重构细节（那属于工作报告）。

### 4.2 工作报告（`reports/`）——读者是维护者与接手者

1. **报告头表**：报告日期 / 项目 / 版本（git 短哈希）/ 对应更新记录。
2. **范围**：本轮做了什么、依据是什么。
3. **交付结论表**：`级别 | 问题 | 状态 | 关键证据`——证据必须可复核（测试文件名、命令输出）。
4. **工程状态**：逐条列出实际跑过的门禁与真实数字。
5. **确认无问题的部分**：查证过没问题的写下来，避免重复排查。
6. **已知限制与未做项**：分「需要人工操作的」「代码侧待办」「固有限制」三类。
7. **下一步建议**：按优先级排序，每条可独立执行。

### 4.3 审计（`audits/`）

范围与方法；逐条结论（`严重程度 | 位置 file:line | 问题 | 建议`）；**已核实无问题的清单**；汇总。
审计是某一天的快照，顶部注明"结论可能已被后续迭代改变"。

### 4.4 手册 / 交接 / 路线图

- 手册：适用场景、前置条件、可复制的命令、常见故障与排查顺序。
- 交接（`HANDOVER.md`）：现状一句话、最近实质性变更、**最容易踩的坑**、接手第一步检查清单、
  指向路线图的链接。
- 路线图：当前基线（版本、测试数）、阶段划分、每项带 `☐ / ✅ 提交哈希`、验收标准、**贯穿约定**；
  已完成项保留不删；新路线图替代旧路线图时旧的在顶部标注并说明。

## 五、链接与引用

1. 跨文件引用写仓库根相对路径（`docs/guides/BUILD_GUIDE.md`）；站内链接必须可点击。
2. 引用代码位置写 `lib/foo.dart:123` 形式。
3. 移动或重命名文档后必须做链接自查，并在提交信息里写明范围。

## 六、提交前检查清单

- [ ] 标题明确了"这是什么"，不是"记录""说明"这类空标题
- [ ] 头部有状态/日期
- [ ] 所有数字都有来源，没有估算值
- [ ] 未做项与已知限制已单列
- [ ] 没有密钥、Token、真实隐私数据（截图里也要检查）
- [ ] 新文档已登记进 `docs/README.md` 的对应章节
- [ ] markdown 链接自查通过（对每个 `](` 目标核对存在）
- [ ] **git status 只含 markdown 与 CHANGELOG.md**——文档绝不碰代码/构建/CI 配置

## 七、模板

### 7.1 更新记录

```markdown
# 更新说明 · <YYYY-MM-DD>（<主题>）

> <2–5 行引语：用户能感知什么、修掉了什么隐患。>

| 项         | 值                                                    |
| ---------- | ----------------------------------------------------- |
| 版本       | git `<短哈希>`（<HH:MM> CST）                         |
| 平台       | Linux（容器内验证）；Windows/macOS/Android 待 CI 验证 |
| 自动化测试 | **<N> 文件 / <M> 用例全绿**（上轮 <n>/<m>，+<d>）     |
| 静态检查   | flutter analyze 通过（<告警数> 条）                   |
| CI         | <run 结论/链接，或"未触发">                           |

## 一、<面向用户的变化>
## 二、<修复与根因>
## 三、已知取舍
```

### 7.2 工作报告

```markdown
# 工作报告 · <YYYY-MM-DD>（<主题>）

| 项           | 值                                                 |
| ------------ | -------------------------------------------------- |
| 报告日期     | <YYYY-MM-DD>                                       |
| 版本         | git `<短哈希>`                                     |
| 对应更新记录 | [`RELEASE_<日期>.md`](releases/RELEASE_<日期>.md)  |

## 1. 本轮范围
## 2. 交付结论（表：级别|问题|状态|关键证据）
## 3. 工程状态（实测）（表：门禁|结果）
## 4. 确认无问题的部分
## 5. 已知限制与未做项
## 6. 下一步建议
```

## 八、维护这份规范

- 新增文档类型时，先在本文档补一节再写第一份实例。
- 操作成本过高的约定就补工具（如链接检查脚本），不要靠"记得改"。
- 修改规范时，提交信息写清"为什么改"和"受影响的既有文档是否已回补"。
